## Warnings

- **Time boundary (stable).** This is a negative case below the minimum lead time (`≥ 6 h`, `06 — Business Rules` § 1.4). The window starts about 2 h after Pre 04, minus up to 59 s from flooring to the minute. Time passing between create, validate and submit only shortens the lead time, so it stays far below 6 h. No margin issue. The actual lead time at submit is slightly under 2 h, not exactly 2 h.
- **Environment variable type.** In the reused environment, `operatorPassword` has type `default`, not `secret`. Its value is empty and the password comes only from `--env-var`, so nothing is stored. To mask it in the Postman UI, change the type to `secret` there yourself. This skill does not edit existing environments.
- **Window near midnight / curfew:** not relevant. `DNI-OPN-1` has no curfew.
- **Collection listing.** `getCollections` (unfiltered) and `getWorkspace` returned `500`. The name check used `getCollections` with an exact-name filter, which returned no match, so the collection was created once.
- **Not run.** The scripts were syntax-checked locally only. `pm.execution.skipRequest()` needs a recent Postman CLI / runtime.

## Open questions

- **Lead time on `validate`:** `06 — Business Rules` § 1.4 measures lead time "between submission and `window_start`". `validate` is not a submission. The code (`lib/gates/time-window-gate.ts:17-22`) measures from "now" for `validate`, and the case relies on that. The docs do not say this explicitly. Built from the case.
- **`message` text:** the case asserts only a non-empty string. The code returns `Window starts less than 6 hours from now.` An exact-text check could be added if the case fixes the text. Not added.
- **Checks suggested but not added (not in the Expected result):**
  - Step 4: `failing_gate` = `TIME_WINDOW`, `rule_reference` = `TSD-4 §2.1`, `submitted_at` non-null on the stored request (`FlightRequest` schema).
  - Step 2: `failing_gate` / `rule_reference` still `null` after `validate`. This would show that the dry run wrote nothing.
  - Step 5: a final `GET` to confirm the state is still `REJECTED` after the `409`.
- **Pilot `full_name`:** required by `CreatePilotInput` (`openapi.yaml`) but missing from the case's Test data. Used `QA Pilot 005`. Suggest adding it to the case.

## How to run (Postman CLI)

Run the **local copy** with a **logged-out** Postman CLI (`postman whoami` shows no account, `POSTMAN_API_KEY` not set) and from a folder outside the repo. A run by cloud uid, or any run while logged in, is uploaded to Postman Cloud with request bodies; `--no-report-events` does not stop that (CLI 1.87.0, run `…-2026-11-09-0123`). `baseUrl` (from `Skypermit-vercel`) goes in with `--env-var` instead of `-e`. Secrets come from environment variables of the shell, never from the command text itself. The usual way is the `postman-cli-run` skill, which checks all of this before it runs.

```bash
# bash (from a folder outside the repo)
export SKY_OPERATOR_PASSWORD='...'   # min 8 chars
postman collection run "<absolute path to repo>/postman/SKY-2/API-OP-005.postman_collection.json" \
  --env-var "baseUrl=https://skypermit.vercel.app/api/v1" \
  --env-var "operatorPassword=$SKY_OPERATOR_PASSWORD" \
  --no-report-events
```

```powershell
# PowerShell (from a folder outside the repo)
$env:SKY_OPERATOR_PASSWORD = '...'   # min 8 chars
postman collection run "<absolute path to repo>\postman\SKY-2\API-OP-005.postman_collection.json" --env-var "baseUrl=https://skypermit.vercel.app/api/v1" --env-var "operatorPassword=$env:SKY_OPERATOR_PASSWORD" --no-report-events
```

Pass one `--env-var "<name>=<value>"` per non-secret variable and per secret variable of the environment.
