# Test design: EP, BV, ST

Бере один файл специфікації (і, за бажанням, правило чи розділ у ньому) і будує тест-дизайн трьома техніками:
класи еквівалентності (EP), граничні значення (BV) і переходи станів (ST). Результат — один JSON-файл.

Головна ідея: **кожен елемент дизайну має бути перевірний по тексту.** Хтось інший відкриє специфікацію на вказаному рядку
й побачить там рівно ту цитату, яку ти навів. Усе, що не можна так підтвердити, — не елемент дизайну, а питання в `unknowns`.
Тест-дизайн, у якому частина очікувань домислена, гірший за коротший, але чесний: домислене очікування потім стає
«зеленим» тестом, що перевіряє не те.

## Вхід

- `$1` — шлях до файлу специфікації (будь-який текстовий формат: md, txt, adoc тощо).
- `$2…` (необов'язково) — правило, розділ або параметр, на якому зосередитись (`focus`).
  Якщо focus вказано — дизайн лише для нього; решту файлу читай тільки як контекст для розуміння цього правила.
  Якщо не вказано — дизайн для всього файлу.

Працюй **лише з цим файлом**. Не читай інших документів, коду, вікі чи трекерів, навіть якщо специфікація на них посилається:
посилання на інший документ — це прогалина для `unknowns`, а не привід піти його читати. Цитата має бути з цього файлу.

## Порядок роботи

1. **Прочитай файл повністю** через Read. Номери рядків бери саме з виводу Read (нумерація з 1).
2. **Знайди focus** (якщо є) — Grep допоможе. Визнач рядки, що його описують.
3. **Параметри й обмеження.** Випиши кожен параметр, для якого текст задає допустимі значення (діапазон, мінімум, максимум,
   перелік, умова «строго після»).
4. **EP** — класи еквівалентності для кожного параметра (див. правила нижче).
5. **BV** — по одній записі на кожну межу кожного діапазону, у кожній записі три значення.
6. **ST** — якщо текст визначає стани й переходи між ними: повна матриця стан × дія. Якщо ні — `not_applicable`.
7. **tests** — перелік майбутніх тестів, що разом покривають усі EP, BV і ST.
8. **unknowns** — усе, чого текст не каже, але що потрібно для очікуваного результату.
9. **Самоперевірка** (список нижче), потім запиши файл.
10. **Візуалізація покриття** — запусти рендер (див. «Після запису»).

## Вихідний файл

Ім'я — `<назва>.design.json`, де `<назва>` — ім'я файлу специфікації без розширення; кладеться **в ту саму теку**, що й специфікація.
Наприклад, `docs/rules.md` → `docs/rules.design.json`. Якщо файл уже існує — перезапиши його.

Формат (значення — лише ілюстрація):

```json
{
  "spec": "<шлях до файлу специфікації>",
  "focus": "<правило або розділ, якщо вказано>",
  "equivalence_classes": [
    {"id": "EP-01", "parameter": "<параметр>", "class": "8–64 символи", "valid": true, "representative": "20 символів",
     "quote": {"line": 12, "text": "<дослівний рядок зі специфікації>"}}
  ],
  "boundary_values": [
    {"id": "BV-01", "parameter": "<параметр>", "boundary": "8 символів", "inclusive": true, "step": "1 символ",
     "values": [
       {"value": "7 символів", "expected": "invalid"},
       {"value": "8 символів", "expected": "valid"},
       {"value": "9 символів", "expected": "valid"}
     ],
     "quote": {"line": 12, "text": "<дослівний рядок зі специфікації>"}}
  ],
  "state_transitions": {
    "states": ["<стан>"], "actions": ["<дія>"],
    "matrix": [{"id": "ST-01", "from": "<стан>", "action": "<дія>", "result": "legal | illegal | unknown", "to": "<стан або null>",
                "quote": {"line": 30, "text": "<дослівний рядок зі специфікації>"}}]
  },
  "tests": [{"id": "T-01", "covers": ["BV-01", "EP-01"]}],
  "unknowns": [{"id": "U-01", "question": "<чого текст не каже>", "affects": ["BV-01"]}]
}
```

Уточнення до формату:
- `spec` — шлях так, як його передав користувач. `focus` — рядок із запиту або `null`, якщо focus не вказано.
- Ідентифікатори — `EP-01`, `BV-01`, `ST-01`, `T-01`, `U-01`, наскрізна нумерація без пропусків (`EP-100`, якщо їх понад 99).
- `inclusive` — `true` / `false` з тексту або `null`, якщо текст цього не каже.
- `response` — необов'язкове поле, лише коли текст називає реакцію системи (див. нижче):
  `"response": {"value": "<код або текст із специфікації>", "quote": {"line": N, "text": "..."}}`.
  Його можна ставити на клас EP, на окреме значення в `values` або на клітинку ST.
- Інших полів не додавай: споживачі цього файлу читають саме цю структуру.
- Текстові поля (`class`, `representative`, `question` тощо) пиши мовою запиту користувача; `quote.text` — завжди мовою оригіналу, бо це копія.

## Правила

### Цитати

- До **кожного** класу, межі й переходу — `quote` з номером рядка й дослівним текстом.
- `quote.text` — це неперервний фрагмент рядка `line`, скопійований посимвольно: з тими самими лапками, тире, бектиками,
  зірочками, `|`, пробілами й регістром. Не виправляй опечаток, не нормалізуй «–» на «-», не прибирай markdown-розмітку,
  не склеюй два рядки. Можна взяти весь рядок або його частину, але частину — без пропусків усередині.
- Якщо правило розтягнуте на кілька рядків — бери той рядок, у якому стоїть саме обмеження (число, слово «inclusive» тощо).
- Чому так суворо: цитату перевіряють механічно, пошуком підрядка в рядку. Перефразована цитата — це вже твоє тлумачення,
  і рецензент не може відрізнити його від тексту.

### Не вигадувати

- Що не написано — те не стає класом, межею, переходом чи очікуваним результатом. Воно йде в `unknowns`.
- **Не додавай класів, яких текст не визначає**: порожнє значення, `null`, неправильний тип, від'ємні числа, спецсимволи тощо.
  Якщо текст про такі значення мовчить — **одне** питання в `unknowns` (на всю специфікацію або focus), у `affects` —
  параметри/елементи, яких це стосується. Якщо текст про них таки каже — це звичайний клас із цитатою.
- Значення поза межами діапазону («менше за мінімум», «більше за максимум») — це клас, який текст визначає самим діапазоном;
  його додавати треба (`valid: false`) і цитата — той самий рядок, що й для діапазону.

### Граничні значення

- На кожну межу — окремий запис BV, і в ньому **рівно три** значення: на один крок менше за межу, сама межа, на один крок більше.
  Діапазон 8–64 символи дає два записи: межа 8 (7, 8, 9) і межа 64 (63, 64, 65).
- **Крок** — найменша одиниця, у якій текст виражає цей параметр: хвилини → 1 хв, грами → 1 г, символи → 1 символ,
  роки → 1 рік. Якщо одиниць у тексті кілька (години й хвилини) — менша. Пиши крок у полі `step`.
- **Включність — лише з тексту.** Однозначні маркери:
  - включна: «inclusive», «включно», «≤», «≥», «at least», «at most», «no more than», «no less than», «не менше», «не більше», «мінімум», «максимум»;
  - невключна: «strictly», «строго», «<», «>», «more than», «less than», «above», «below», «понад», «більше ніж», «менше ніж».
  - **Неоднозначні без уточнення**: «between», «від … до», «X–Y», «up to», «до», «within», «after», «before». Для них `inclusive: null`.
- Якщо включність невідома, `unknown` отримує **лише значення, що залежить від неї** — сама межа. Сусіди лишаються визначеними,
  бо їхня доля від включності не залежить:
  - нижня межа L: `L−1` → invalid, `L` → unknown, `L+1` → valid;
  - верхня межа U: `U−1` → valid, `U` → unknown, `U+1` → invalid;
  - і питання в `unknowns` про цю межу.
- Межа «строго після / строго більше» (наприклад, кінець строго після початку): межа — рівність, `inclusive: false`,
  значення — «на крок раніше» invalid, «рівно» invalid, «на крок пізніше» valid.
- `expected` — лише `valid`, `invalid` або `unknown`.

### Реакція системи на порушення

- Що саме повертає система (код відповіді, текст помилки, поле), пиши **лише** якщо це є в тексті — полем `response` з цитатою.
- Якщо текст цього не каже — поля не пиши, а додай **одне** питання в `unknowns` на параметр
  («Що повертає система, коли <параметр> поза діапазоном?»), з `affects` на всі елементи цього параметра.

### Стани й переходи

- `states` — усі стани, які текст називає для об'єкта у focus. `actions` — усі дії/події, що в тексті переводять об'єкт між станами
  (зокрема автоматичні, якщо текст показує їх як переходи).
- `matrix` — **повна** таблиця: рівно одна клітинка на кожну пару (стан, дія), тобто `len(states) × len(actions)` клітинок.
  Порядок — стани в порядку `states`, усередині — дії в порядку `actions`. Повнота важлива, бо саме невказані пари
  (повторна дія, дія з кінцевого стану) і ловлять більшість дефектів.
- `result`:
  - `legal` — текст явно описує цей перехід; `to` — цільовий стан; цитата — рядок із цим переходом.
    Якщо перехід дозволений лише за умови (дедлайн, роль), він усе одно `legal`, а сама умова з межею стає EP/BV.
  - `illegal` — текст забороняє цю пару: прямо, або загальним правилом на кшталт «будь-який інший перехід заборонений»,
    або оголошує стан кінцевим (без виходів). Таке загальне правило — валідна цитата для **кожної** пари, якої немає
    в списку дозволених. `to: null`.
  - `unknown` — пари немає серед дозволених, і загального правила теж немає. `to: null`, цитата — рядок, де перелічено
    переходи зі стану `from` (або сам стан). Плюс питання в `unknowns` з `affects` на ці клітинки (одне питання може
    покривати групу клітинок).
- Якщо станів у тексті (чи у focus) немає — `"state_transitions": {"not_applicable": "<чому>"}`.

### tests

- Перелік майбутніх тестів: кожен має `covers` з одним або кількома id з EP, BV, ST.
- **Жоден клас, межа чи клітинка ST не лишаються без тесту.** Запис BV покривається тестом цілком (усі три значення).
- Комбінуй, де це природно (валідний представник EP + валідне граничне значення), але не зводь кілька невалідних
  елементів в один тест: при першій помилці решта не перевіриться.

### unknowns

- Кожне питання — про одну конкретну прогалину в тексті, сформульоване так, щоб власник специфікації міг відповісти одним реченням.
- `affects` — id елементів, на які впливає відповідь (може бути порожнім, якщо прогалина не прив'язана до жодного елемента,
  наприклад про незгадані порожні значення до появи класів).
- Не дублюй: одна прогалина — одне питання.

## Самоперевірка перед записом

- [ ] Кожен `quote.text` — дослівний підрядок рядка `quote.line` (перечитай рядок, якщо сумніваєшся).
- [ ] У кожному BV рівно три значення: межа−крок, межа, межа+крок; `expected` ∈ {valid, invalid, unknown}.
- [ ] `inclusive` взято з маркера в тексті; там, де маркера немає, — `null`, межа `unknown`, є питання.
- [ ] `response` є лише там, де код/текст відповіді процитовано; на кожен параметр без нього — питання в `unknowns`.
- [ ] Немає класів «порожнє/null/неправильний тип», не визначених текстом.
- [ ] Матриця ST має `states × actions` клітинок, без дублікатів пар.
- [ ] Кожен EP, BV, ST id є хоча б в одному `covers`; кожен id у `covers` і `affects` існує.
- [ ] Файл — `<назва>.design.json` поруч зі специфікацією, валідний JSON.

## Після запису: render-coverage

Останній крок — механічна візуалізація без AI. Одразу після запису JSON запусти:

```
node .claude/skills/test-design/scripts/render-coverage.mjs <шлях до <назва>.design.json>
```

Скрипт кладе поруч `<назва>.coverage.html`: числові лінії параметрів (класи, межі з включністю, точки BV, представники EP),
таблицю стан × дія і трасування цитата → елемент → тест зі списком unknowns. Заодно він звіряє кожну цитату з рядком
специфікації і показує елементи без тесту та биті id.

- `ERR` або ненульовий код виходу — JSON невалідний: виправ його й запусти знову.
- Якщо на сторінці є ✗ у цитатах, «Без тесту» > 0, «Биті id» > 0 або попередження про неповну матрицю ST — це провал
  самоперевірки: виправ JSON і перезапусти скрипт, поки лічильники не стануть чистими.
- HTML не редагуй вручну — він завжди генерується з JSON.

Після цього коротко повідом користувачу: шлях до JSON і до `.coverage.html`, скільки EP / BV / ST / тестів / unknowns,
і 2–3 найважливіші прогалини.
